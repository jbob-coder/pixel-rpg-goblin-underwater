# Unnamed Hunt RPG — Model Reference Image and Creation Pipeline

Status: SELECTED REFERENCE PIPELINE + PROTOTYPE REQUIREMENTS / NO 3D ASSET IMPLEMENTATION
Last reconciled: 2026-09-02

## Purpose

Define exactly which PNG/reference images are needed before a model is created, what each image is allowed to decide, how reference images feed the 3D asset pipeline, which images can be generated by ChatGPT, and which outputs must still be authored/verified in a real 3D/DCC workflow.

This is a bounded quality fix for `MODEL_ART_DIRECTION_AND_ASSET_STANDARD.md`.

It exists to prevent a common production failure: using one attractive concept image as if it were simultaneously an orthographic blueprint, anatomy specification, texture map, scale reference, rig plan and final in-game look.

A concept image is not enough.

---

# 1. Primary quality rule — separate visual intent from technical truth

Every production model needs two kinds of references:

1. **Visual-intent references** — establish style, silhouette, mood, material language, color and broad design.
2. **Technical references** — establish exact scale, repeatable views, anatomy zones, modular seams, break/sever boundaries, equipment attachment locations and modeling constraints.

Generated concept art may be used strongly for visual intent.

Generated images must not silently become technical truth when perspective, dimensions, labels or hidden geometry are uncertain.

The authoritative technical values remain in project data/design documents and later in verified DCC/engine assets.

# 3. Required PNG reference pack for a production monster

A major monster should not enter final modeling from one image.

Preferred reference pack:

## M01 — Hero concept PNG
Purpose:
- species identity;
- primary mass;
- silhouette;
- material/color language;
- obvious crystal/mutation influence;
- emotional/visual direction.

Recommended view:
- strong 3/4 view;
- neutral or readable stance;
- simple background.

Use: visual intent.

Can ChatGPT generate it? **YES.**

Can it be used directly as the model? **NO.**

## M02 — Turnaround PNG
Required views:
- front;
- left side;
- rear;
- right side where asymmetry matters;
- optional top view;
- optional 3/4 confirmation.

Requirements:
- neutral pose;
- same proportions across views;
- minimal perspective distortion;
- plain/transparent or flat neutral background;
- no dramatic foreshortening;
- scale marker shown outside the creature.

Use:
- blockout proportions;
- silhouette matching;
- limb placement;
- tail/wing/horn length relationships.

Can ChatGPT generate it? **YES as a reference candidate, but it must be checked for cross-view consistency.**

For production, the DCC blockout becomes the final geometric authority if generated views disagree.

## M03 — Anatomy segmentation PNG
Purpose:
Map gameplay anatomy onto the visual creature.

Required information:
- stable part IDs;
- clearly colored regions;
- left/right distinction;
- breakable parts;
- severable parts;
- protected/armored regions;
- optional core cavity only if direct-core mechanics are later approved.

Example IDs:
- `HEAD`;
- `HORN_L`;
- `HORN_R`;
- `TORSO`;
- `FORELEG_L`;
- `FORELEG_R`;
- `HINDLEG_L`;
- `HINDLEG_R`;
- `TAIL_BASE`;
- `TAIL_TIP`;
- `WING_L`;
- `WING_R`.

Use:
- hit-region planning;
- mesh/bone grouping;
- break/sever boundaries;
- targeting UI;
- damage-state planning.

Can ChatGPT generate the base creature/overlay? **YES.**

Quality rule:
Generated text labels are not trusted as authoritative IDs. Stable IDs should be overlaid/verified deterministically after generation or referenced from the Markdown/data specification.

## M04 — Damage-state PNG
Required examples for every important breakable/severable structure:
- intact;
- wounded;
- broken;
- severed where legal;
- destroyed where legal.

Purpose:
- determine what geometry swaps are needed;
- determine sever-cap design;
- ensure the result remains recognizable;
- ensure harvest condition can be visually communicated.

Can ChatGPT generate it? **YES as visual design reference.**

The domain rules, not the PNG, decide legal state transitions.

## M05 — Crystal/mutation variant PNG
Purpose:
Show how one base species changes through approved mutation families without becoming an unrelated creature.

Possible panels:
- baseline;
- terrain adaptation;
- elemental adaptation;
- armor/skeletal mutation;
- sensory mutation;
- berserk visual state.

Rule:
Mutations must preserve identifiable species lineage unless a future explicit transformation mechanic says otherwise.

Can ChatGPT generate it? **YES.**

## M06 — Material/color breakdown PNG
Purpose:
Separate visible material families:
- hide;
- scale;
- bone/horn;
- plate/shell;
- membrane;
- claws;
- crystal/mineral tissue;
- scars/wounds.

Include approximate palette/value families, not just RGB decoration.

Can ChatGPT generate it? **YES for visual reference.**

Do not treat generated normal/roughness/ORM-looking images as production-ready texture maps.

## M07 — Scale comparison PNG
Show:
- 1.7–1.8 m human reference;
- monster side silhouette;
- exact design target length/height values written outside the generated creature;
- optional doorway/tree/rock reference.

Purpose:
Prevent scale drift between concept art and actual world units.

Can ChatGPT generate the composition? **YES.**

Authoritative measurements come from the recorded numeric design, not visual estimation from the PNG.

## M08 — In-game readability PNG
Three panels minimum:
- aerial exploration camera;
- normal nearby exploration;
- first-person combat.

Purpose:
Verify the creature still reads correctly at all three intended gameplay distances.

Can ChatGPT generate it? **YES.**

This is a visual target, not proof of actual engine camera/FOV/readability.

## M09 — LOD silhouette PNG
Panels:
- LOD0;
- LOD1;
- LOD2;
- optional LOD3/impostor silhouette.

Purpose:
State what must survive simplification:
- species silhouette;
- major anatomy;
- broken/severed state readability;
- dangerous attack structures.

Can ChatGPT generate it? **YES as concept reference.**

Actual LOD geometry must be produced from the real mesh and profiled on device.

# 4. Required PNG reference pack for the player/humanoid character

## H01 — Hero concept
- front/3/4 visual identity;
- practical frontier-hunter clothing;
- readable weapon/equipment silhouette.

## H02 — Neutral turnaround
- front;
- side;
- back;
- neutral A/T pose as required by future rig workflow;
- scale marker.

## H03 — Modular equipment sheet
Separate visual groups for potential modular construction:
- base body/underlayer;
- torso;
- shoulders;
- arms/gloves;
- waist/belt;
- legs;
- boots;
- headgear;
- back gear;
- weapon/tool.

This does not lock gameplay equipment slots; it defines art separability.

## H04 — Silhouette/loadout sheet
Show several approved loadout silhouettes at aerial distance.

Purpose:
Verify that the player's equipment choice is recognizable without relying on UI.

## H05 — Material/color sheet
Define cloth, leather, metal, wood, bone/crystal accents and controlled palette hierarchy.

## H06 — In-game readability sheet
Show aerial, nearby exploration and first-person-hand/weapon context where relevant.

All of these may be generated as reference PNGs, but final rig/model proportions must be verified in the DCC and game camera.

# 5. Required PNG reference pack for buildings

A building needs more than a beauty illustration because the settlement is physically walkable.

## B01 — Exterior hero concept
3/4 view showing function and silhouette.

## B02 — Orthographic elevation sheet
- front;
- rear;
- left;
- right.

Use for modular planning and facade consistency.

## B03 — Roof/top-plan PNG
Purpose:
- roof shape;
- courtyard relationship;
- entrance locations;
- camera occlusion/cutaway planning.

## B04 — Floor-plan/blockout PNG
Must show actual planned dimensions in meters outside/along the plan.

Use for:
- walkability;
- room scale;
- doors/stairs;
- service placement;
- collision/blockout.

Generated artistic floor plans are not authoritative unless dimensions are separately validated.

## B05 — Interior cutaway PNG
Show the building with roof/walls removed enough to understand the walkable interior.

## B06 — Modular-kit breakdown PNG
Show which pieces are reusable:
- walls;
- corners;
- roof modules;
- beams;
- foundations;
- doors/windows;
- stairs;
- balconies;
- chimneys;
- awnings;
- fences.

## B07 — Three-distance readability PNG
- aerial settlement view;
- street/exploration view;
- interior view.

ChatGPT can generate all seven as visual/reference images. Exact meter dimensions, collision and modular snapping must be verified in the blockout/DCC/engine.

# 6. Required PNG reference pack for environment/terrain modules

For an environment family, use:
- biome mood/identity sheet;
- cliff/rock family sheet;
- tree/vegetation family sheet;
- riverbank/water-edge sheet;
- cover-object sheet;
- path/ground-material sheet;
- track/sign examples;
- terrain hazard examples;
- distance/LOD sheet.

Do not generate thousands of unique props before a reusable environment kit is proven.

# 7. What PNGs may be used directly in the game

Some PNGs are suitable as runtime assets when deliberately designed for that purpose.

Potential direct-use PNG categories:
- UI icons;
- map symbols;
- field-guide/bestiary illustrations;
- contract illustrations;
- portraits where the art direction chooses 2D portraits;
- decals/masks after technical cleanup;
- billboards/impostors generated from verified 3D renders;
- splash/title/concept artwork;
- simple VFX sprites where technically appropriate.

Generated concept PNGs should **not automatically** be used directly as:
- exact PBR base-color textures for a model;
- normal maps;
- ORM/metallic/roughness maps;
- UV layouts;
- anatomy hit masks;
- collision maps;
- navigation maps;
- exact orthographic geometry blueprints;
- LOD meshes.

Those require a controlled technical asset pipeline.

# 8. Recommended model creation pipeline

For a hero monster:

`DESIGN DATA`
→ `REFERENCE PNG PACK`
→ `REFERENCE REVIEW`
→ `GRAYBOX/BLOCKOUT`
→ `SCALE CHECK IN WORLD UNITS`
→ `AERIAL + FIRST-PERSON CAMERA CHECK`
→ `ANATOMY REGION CHECK`
→ `HIGH-POLY/FORM PASS`
→ `GAME-READY RETOPOLOGY`
→ `UV UNWRAP`
→ `BAKE`
→ `PBR TEXTURE AUTHORING`
→ `RIG`
→ `BREAK/SEVER ATTACHMENT SETUP`
→ `COLLISION + ANATOMY HIT PROXIES`
→ `LOD GENERATION`
→ `ENGINE IMPORT`
→ `AUTHORITATIVE STATE BINDING`
→ `ANDROID DEVICE TEST`
→ `FIX/OPTIMIZE`
→ `PRODUCTION APPROVAL`

Do not skip the graybox/camera/anatomy checks because a concept looks attractive.

---

# 9. Model graybox acceptance gate

Before high-poly work begins, the blockout must prove:
- correct world-unit scale;
- readable aerial silhouette;
- convincing first-person apparent scale;
- major anatomy visible enough to target;
- legal break/sever boundaries possible;
- locomotion has enough joint clearance;
- body mass does not intersect itself badly during basic poses;
- intended cover/terrain interactions remain plausible;
- camera can frame the monster without excessive clipping;
- no critical part depends on tiny detail invisible on phone.

A failed graybox returns to design/blockout. Do not solve it with more texture detail.

---

# 10. Reference-image versioning

Each important reference should eventually use a stable ID and revision.

Example:
`MONSTER_M01_HERO_CONCEPT_v003.png`
`MONSTER_M02_TURNAROUND_v002.png`
`MONSTER_M03_ANATOMY_v005.png`

Recommended metadata stored beside it:
- content/entity ID;
- purpose;
- revision;
- status: CONCEPT / SELECTED / SUPERSEDED / TECHNICALLY_VERIFIED;
- source/provenance;
- linked design doc;
- dimensions/resolution;
- notes/open contradictions.

Never silently replace a selected reference without updating its revision/status.

---

# 11. Recommended PNG dimensions

These are working recommendations, not engine texture budgets.

For concept/reference images:
- hero concept: 1536–2048 px long side or larger when useful;
- turnaround/model sheets: ideally 2048–4096 px canvas;
- anatomy/damage/material sheets: 2048 px+ where labels/regions must remain readable;
- building/floor-plan sheets: 2048–4096 px depending complexity;
- quick exploratory thumbnails may be smaller.

Runtime texture resolution is a separate decision and must come from engine/device profiling.

Do not confuse a 4096 px modeling reference with permission to use a 4K runtime texture on Android.

---

# 12. Transparent-background rule

Use transparent PNGs when:
- isolating character/monster silhouettes;
- building turnarounds;
- comparing mutations/equipment;
- creating later UI/bestiary cutouts.

Use flat neutral backgrounds when:
- transparency creates edge/readability problems;
- material/value judgment is important;
- the image is primarily an art-direction board.

Environment/in-game-view references should use actual scene context rather than transparency.

---

# 13. Labeling rule

Because generated image text can contain errors:
- generated labels are illustrative;
- authoritative IDs/numbers remain in Markdown/data;
- technical labels should be added or verified after generation;
- scale measurements must be copied from recorded design values rather than estimated from image text;
- filenames and metadata carry the authoritative reference identity.

This prevents visual-generation errors from contaminating gameplay data.

# 15. What cannot be honestly claimed from PNG generation alone

A generated PNG does not prove:
- exact orthographic consistency;
- exact meter scale;
- production topology;
- deformation quality;
- UV correctness;
- animation suitability;
- accurate PBR texture maps;
- collision quality;
- anatomy hitbox correctness;
- LOD performance;
- Android runtime performance;
- engine import correctness.

Those require actual 3D assets, tools and device verification.

---

# 16. Application rule

The word **apply** has different meanings and must stay precise.

## Apply as design reference
YES — generated PNGs can immediately guide modeling, blockout, material, composition and design decisions.

## Apply as project documentation
YES — references can be versioned, stored in Drive and linked from authoritative Markdown.

## Apply directly as a 2D runtime asset
YES, only when the asset is intentionally a 2D runtime asset and passes technical cleanup/testing.

## Apply directly to create a finished 3D model automatically
NO — a PNG does not become a production-ready rigged/severable/LOD-tested 3D asset by itself.

The correct path is PNG reference → verified model creation pipeline → engine integration.
